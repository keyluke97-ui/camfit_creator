> 최초 실행 사례: 2026-08-19, 6건 탐지 → 5건 소생 (더쉼오토캠핑장은 환불 접수로 보류)

**요청 트리거**: "죽은 캠페인 살려줘" / "콘텐츠 제작 기한 지난 거 늘려줘" / "기한 연장 + 쿠폰 재발급" — 이 문서의 절차를 그대로 따른다.

## 0. 목적 & 문제 정의

**죽은 캠페인** = 캠지기가 돈을 냈는데 **모집 잔여가 남은 채 콘텐츠 제작 기한이 지난** 캠페인.

이게 왜 방치되는가 — **제작 기한은 캠페인을 마감시키지 않는다.**

```
getCampaigns()        → filterByFormula: '{입금내역 확인}'   ← 기한 조건 없음
isCampaignClosed()    → availableCount < 1 || price < 0      ← 기한 무관
getDeadlineStatus()   → tone='passed' (회색 뱃지 D+N)         ← 표시만 바뀜
```

즉 기한이 67일 지난 캠페인도 **포털에 그대로 노출되고 신청까지 된다.** 크리에이터가 지금 지원하면 기한 내 콘텐츠를 낼 수 없는 협찬에 들어가는 것이고, 캠지기는 낸 돈만큼 못 받는다. 아무 알림도 없으므로 **주기적으로 훑지 않으면 발견되지 않는다.**

## 1. 대상 판정 기준

다섯 조건을 **전부** 만족하는 캠페인만 대상이다.

| 조건 | 필드 | 이유 |
|---|---|---|
| 입금 완료 | `입금내역 확인 = true` | 미입금은 아직 오픈 전 |
| 운영 중 | `Select ≠ 미운영` | 종료된 건 제외 |
| 환불 없음 | `환불 요청일` · `환불 요청 금액` 모두 비어 있음 | 환불 = 마감된 건 |
| 기한 경과 | `콘텐츠 제작 기한 (날짜) < 오늘` | |
| **모집 잔여 있음** | `총 신청 가능 인원 > 0` | **핵심 조건** |

### 미업로드는 대상이 아니다

기한이 지났는데 **신청자는 다 찼고 콘텐츠만 안 올라온 것**은 다른 문제다. 그건 연장이 아니라 **독촉** 대상이고 `tools/content-followup/overdue.cjs`가 담당한다. 죽은 캠페인은 *모집 자체가 안 끝난* 건이다.

### ⚠️ 자동으로 못 거르는 것

`환불 요청일`은 **운영자가 입력해야** 채워진다. 접수는 됐지만 아직 Airtable에 안 들어온 건은 어떤 가드로도 안 걸린다. **대상 목록은 반드시 사람에게 확인받고 진행한다.** (2026-08-19 더쉼오토캠핑장이 이 케이스였다.)

**환불은 철회될 수 있다.** 위 이유로 제외한 건은 나중에 되돌아온다 (더쉼오토는 같은 날 환불 철회 → 연장으로 복귀). 그래서 **Step 3(기한 연장)은 보류 건에도 미리 적용해두는 편이 낫다** — 되돌리기 쉽고(숫자 하나), 환불이 확정되면 어차피 `Select = 미운영`으로 빠져 무해하다. 반면 **Step 5(쿠폰 재발급)는 보류한다** — 캠핏에 실물 쿠폰이 생겨 되돌리려면 어드민에서 지워야 한다. 이 비대칭이 2026-08-19에 실제로 유효했다: 더쉼오토는 기한만 미리 들어가 있어서 철회 후 대표 쿠폰 1개만 발급하면 끝났다.

## 2. 절차

### Step 1 — 탐지 (읽기 전용)

```bash
node tools/campaign-revival/check.cjs   # 🆕 죽은 공고 + D-30 임박 공고 한 번에 (기한 지나기 전 선제 탐지)
node tools/coupon-pool/audit.cjs        # 쿠폰 풀 정합성 선점검
node tools/content-followup/overdue.cjs # 미업로드는 별도 트랙임을 확인
```

> `check.cjs`는 기한이 **아직 안 지난 임박 건(D-30 이내)** 도 함께 뽑는다. 크리에이터 일정이 ~1달 선점되므로 기한 한 달 이내 = 실질 신청 불가. 지나고 나서 소생하는 것보다 임박 단계에서 연장하는 게 싸다 (2026-08-28 회차부터 이 기준).

대상 산출은 아래 조건으로 `캠지기 모집 폼`을 훑는다 (Airtable REST, `.env.local`의 `AIRTABLE_*` 사용).

```
입금내역 확인 = true
  AND Select ≠ '미운영'
  AND 환불 요청일 · 환불 요청 금액 모두 empty
  AND 콘텐츠 제작 기한 (날짜) < today(KST)
  AND 총 신청 가능 인원 > 0
```

> **기준일은 반드시 `date`로 실측한다.** 세션 컨텍스트의 날짜가 실제와 다를 수 있고, 하루만 틀려도 경계 건의 판정이 뒤집힌다.

부가로 **`입실일 > 콘텐츠 제작 기한`인 신청 건**도 뽑아둔다. 연장 없이는 구조적으로 기한 내 콘텐츠가 불가능한 건이라 근거가 된다.

### Step 2 — 대상 확정 (사람 확인)

캠핑장 / D+경과 / 모집·신청·잔여 / 현재 개월수 / 예산을 표로 제시하고 승인받는다. 환불 접수 중인 건이 섞였는지 여기서 확인한다.

> **[2026-08-28 확정 규칙] 쿠폰을 건드리기 전에는 반드시 계획표를 먼저 제시하고 승인받는다.** 표에는 **쿠폰명 + 쿠폰 ID + 어드민 상세 링크**(`https://admin.camfit.co.kr/#/extra-service/host-coupon-list/{쿠폰ID}`) + 현재값→변경값을 포함한다. 어드민은 해시 라우팅 SPA라 링크를 연달아 같은 탭에서 열면 화면이 안 바뀐다 — 새 탭(Cmd+클릭)으로 열라고 안내할 것.

### Step 3 — 제작 기한 연장

```
콘텐츠 제작 기한 (날짜) = Created + (기본 제작 개월수 + 추가 기간 연장) 개월   ← 포뮬러
```

**`추가 기간 연장`(number)만 수정한다.** 기한 필드는 포뮬러라 자동으로 따라오고, 표시용 `⏰ 콘텐츠 제작 기한`도 같은 수식을 공유하므로 두 값이 어긋나지 않는다.

기준일이 **Created(신청일)** 이므로 오래된 캠페인일수록 더 많이 넣어야 한다. **일괄 +N을 그대로 적용하지 말고 결과 날짜를 캠페인별로 계산해 확인한다.** (2026-08-19: 3월 신청 건은 +3으로도 D-25밖에 안 나와 +5를 적용했다.)

**목표**: 방문 마감 + 콘텐츠 제작 14일이 새 기한 안에 들어올 것.

> 🆕 Step 3~4는 `node tools/campaign-revival/extend.cjs`(드라이런) → `--apply`로 자동화됨 (2026-08-28).
> 실행 전 스크립트 상단 `TARGET`(목표 기한)을 이번 회차 값으로 수정. 쿠폰이벤트 캠페인의 날짜 4개 갱신(방문종료 = min(오늘+방문일수, 새기한−14일) 클램프)과 SOP Step 6 가드·재조회 검증까지 포함한다.
> ⚠️ **날짜/epoch를 암산하지 마라.** 2026-08-28 회차에서 목표 epoch 암산이 12-10 대신 11-28로 틀렸었다(서버 에러 덕에 미적용). 항상 `Date.parse('YYYY-MM-DDT23:59:59+09:00')`처럼 코드로 계산하고 역변환으로 재확인.

### Step 4 — 방문 가능 / 쿠폰 유효 기간 갱신 (쿠폰이벤트 캠페인만)

`쿠폰이벤트희망 = true`면 날짜 4개를 같이 밀어야 한다. **기존 규칙을 재사용한다**:

| 필드 | 값 |
|---|---|
| `크리에이터 방문 가능 시작일` | 오늘 |
| `크리에이터 방문 가능 종료일` | 시작 + **60일** (`방문 가능 기간(일수)`) |
| `쿠폰 유효 시작일` | 오늘 |
| `쿠폰 유효 종료일` | 시작 + **104일** (`쿠폰 유효 기간(일수)`) |

🔴 **비우지 말고 교체한다.** `lib/airtable.ts`의 `hasAllCouponFields` 가드가 이 4개 중 하나라도 비면 `couponEvent`를 통째로 undefined로 만들어 **카드가 조용히 일반 캠페인으로 렌더된다** (`console.warn`만 남고 화면엔 흔적 없음).

🔴 **Airtable 날짜 = 캠핏 쿠폰의 실제 날짜여야 한다.** 이 값들은 포털에 그대로 표시되는 동시에 쿠폰 발급 파라미터다. 자동 발급 경로에서는 자동화가 같은 필드를 읽어 `activeTimestamp`/`expireTimestamp`로 넘기므로 구조적으로 일치하지만, **수기 발급은 그 연결이 끊기므로 사람이 일치를 보장해야 한다.**

### Step 5 — 쿠폰 재발급

> 🔴 **[2026-08-28 확정] 쿠폰 "만료일 수정"이라는 기능은 존재하지 않는다 — 재발급이 유일한 경로다.**
> 실측 근거: `PUT /coupons/{id}`는 `downloadExpireTimestamp`(다운로드 기한)만 반영하고 `expireTimestamp`(사용/입실 만료)는 조용히 무시한다. 어드민 웹 수정 화면(host-coupon-detail 번들)도 update 시 다운로드 기간만 보낸다 — 사용 기간은 생성 시에만 설정 가능. "기간 연장해줘" 요청이 와도 절차는 언제나 **신규 발행 + 코드 교체**다.

#### [2026-08-28] 재발급 실행 레시피 (2차 실행에서 확립)

1. **옛 쿠폰 상세 GET** (`GET /coupons/{id}`) → 그 JSON을 통째로 복제해 create payload를 만든다. 제거: `id`/`numOfIssued`/`numOfUsed`/`zones`. 추가: `campId`·`targetCodes`(= 캠페인의 `🎟️ 캠핏 캠핑장 ID`), `masterCode:null`·`issueCode:null`(서버 생성). 교체: 타임스탬프 4개(사용 시작/만료 + 다운로드 시작/만료). `NaN:NaN` 시간값은 `00:00`/`23:59`로 보정.
2. **날짜 규칙**: 대표 쿠폰 = 오늘 ~ `크리에이터 방문 가능 종료일`(입실이 방문기간 안이어야 함) / 팔로워 쿠폰 = 오늘 ~ `쿠폰 유효 종료일`. 두 기간(사용·다운로드) 동일하게.
3. **🔴 존 타겟 승계 확인**: `target`이 `zone`인 캠핑장이 있다(실례: 파머스힐 대표 쿠폰, `zoneIds` 5개). 복제 시 `target`+`zoneIds`+`zoneNames`가 그대로 넘어가는지, 발행 후 상세 재조회로 존 개수까지 검증할 것. 놓치면 전체 존에 100% 할인 쿠폰이 풀린다.
4. **발행 경로**: camfit-admin-plugin MCP `camfit_coupon_create`(payload를 `POST /coupons`에 그대로 전달). 어드민 API 401이면 `camfit_login_web` env=production으로 재로그인(브라우저 세션 재사용). 이 세션 계열은 `.claude/settings.local.json`에 create/delete 허용 등록됨.
5. **발행 후 전 장 상세 재조회 검증**: 날짜 4개·할인·한도·인당사용·박수·target/존 개수를 옛 쿠폰과 대조.

#### [2026-08-28] 배포분 처리 정책 (사장님 확정)

- **이미 배포된 팔로워 쿠폰은 절대 재발급/변경하지 않는다.** 판정 기준은 다운로드 수가 아니라 **신청 레코드로 배포됐는지**다(다운 0이어도 배포됐으면 제외). 이유: 배포한 크리에이터의 콘텐츠 상세에 쿠폰 조건(기간)이 이미 명시돼 있어, 실물을 바꾸면 콘텐츠와 어긋난다.
- **대표(크리에이터) 쿠폰은 다운/사용이 있어도 재발급한다.** 캠페인당 1장을 전원이 공유하는 구조라, 새로 매칭될 크리에이터가 쿠폰을 받으려면 살아있는 대표 쿠폰이 필요하다. 기존에 받아간 크리에이터의 유저 쿠폰은 발급 시점에 확정돼 있어 영향 없다.
- **옛 쿠폰 정리**: 미배포 팔로워(발급 0 재확인 후)만 `camfit_coupon_delete`로 삭제. **옛 대표 쿠폰은 삭제 금지** — 삭제는 발급된 유저 쿠폰을 회수한다. 자연 만료로 방치.

쿠폰은 **두 종류이고 발급 단위가 반대다.**

| | `쿠폰코드` (대표) | `팔로워 쿠폰 코드` (풀) |
|---|---|---|
| 정체 | 크리에이터 본인 예약용 | 크리에이터가 팔로워에게 뿌리는 것 |
| 단위 | **캠페인당 코드 1개**를 전원이 공유 | **코드 N개**, 1인 1코드 |
| 수량 | 발급 한도 ≥ **잔여 인원** | **미배포 개수**(= 열린 자리)만큼 |
| 대상 | 전 캠페인 (없으면 신청이 `COUPON_NOT_FOUND`로 막힘) | `쿠폰이벤트희망 = true`만 |
| 자동화 | 없음 → 어드민 수기 | 「쿠폰 자동 발행 (프리미엄)」 `wfl30wtAD1Z9y3Mtm` |

**복사할 값은 `issueCode`** — 팔로워가 앱에 입력하는 코드다. `masterCode`는 어드민 식별자이고 자동화도 `detail.issueCode || detail.masterCode` 순으로 고른다. 기존 코드처럼 `_` + 8자 형태면 맞다.

#### 자동화를 쓸 수 있는가 — 현재는 아니다

「쿠폰 자동 발행 (프리미엄)」에는 결함 2개 + 만료 이슈가 있다.

1. 🔴 **JWT 하드코딩 · 반복 만료** — input variable에 정적 토큰. §29(핸드오버) 기준 2026-05-28 · 07-08 · 08-02 **3회 만료**. 만료 상태로 켜면 전건 401 → `발행 상태 = 실패`.
2. 🔴 **풀을 통째로 덮어쓴다** — `"팔로워 쿠폰 코드": successCodes.join("\n")`. `배포 완료된 쿠폰`은 그대로 남아 이중 유통이 된다.
3. 🔴 **총 모집 인원 전량을 재발행한다** — 잔여가 아니라 `⭐️+✔️+🔥 모집 인원` 합. 배포완료가 있는 캠페인은 필요 수량보다 많이 만든다.

→ **셋 다 해결되기 전에는 수기 발급 후 미배포분만 1:1 교체**가 안전하다.

#### 수기 발급 파라미터 (자동화 body와 동일하게)

`할인 금액`(정액) · `인당 팔로워 쿠폰`(코드당 사용 인원) · `쿠폰 적용 요일` · `사용가능 최소/최대 예약 박수` · `🎟️ 캠핏 캠핑장 ID` · Step 4에서 정한 유효기간.
쿠폰명은 **18자 제한**이라 `팔로워 쿠폰 (` + 캠핑장명 9자 + `)`.

### Step 6 — Airtable 반영 + 검증

`쿠폰코드`는 교체, `팔로워 쿠폰 코드`는 **미배포분만 새 코드로 교체하고 `배포 완료된 쿠폰`은 절대 건드리지 않는다.**

쓰기 전 가드:
- 불변식 **`풀 줄 수` ≥ `총 신청 가능 인원`** ([SOP-쿠폰풀-정합성](SOP-프리미엄협찬-쿠폰풀-정합성.md))
- 새 코드에 중복 없음 · `배포 완료된 쿠폰`과 겹치지 않음
- 대표 쿠폰코드가 빈 값이 되지 않음
- `🎟️ 쿠폰 자동 발행 = false` (자동화 오발사 방지)
- 환불 진행 건 아님

쓰기 후 **재조회로 실제 값 확인** + 불변식 + `hasAllCouponFields` 재현. 마지막에 `node tools/coupon-pool/audit.cjs`로 전수 재검증.

`🎟️ 발행 결과 로그` 맨 앞에 수기 발급 사실을 남긴다 — 기존 자동화 로그는 아래 보존. 수기 발급분은 `🎟️ 발행된 쿠폰 ID 리스트`에 안 들어가므로 기록이 없으면 나중에 역추적이 끊긴다.

### Step 7 — 뒤처리 (사람)

- **옛 쿠폰 만료 처리** — Airtable에서 코드를 지워도 캠핏 쿠폰은 살아 있다. 교체된 대표·팔로워 코드를 어드민에서 비활성/삭제.
- **이미 배포된 팔로워 쿠폰**은 판단 대상이다. 기한을 늘리면 포털은 새 날짜를 표시하는데 그 쿠폰들의 실제 만료일은 옛날이다. 둘 중 하나를 고른다:
  - 어드민에서 **만료일만 연장** (표시와 실제를 맞춤)
  - **그대로 둠** — 해당 크리에이터가 이전 조건을 인지하고 이미 움직였다면 합리적 (2026-08-19 선택)

## 3. 함정 모음

- **오늘 날짜를 실측하라.** 세션 컨텍스트 날짜와 머신 시각이 다를 수 있다. 하루 차이로 경계 건 판정이 뒤집힌다.
- **캠핑장 레코드는 중복된다** (재신청). 같은 이름으로 여러 레코드가 있고 업로드·쿠폰이 각기 다른 레코드에 걸린다. **집계는 반드시 레코드 ID 기준.** 이름으로 조인하면 미완료 건을 완료로 오판한다.
- **`⭐️/✔️/🔥 협찬 제안 금액`은 모집 인원 0인 등급에서 음수로 나온다** (포뮬러 특성). 열린 등급만 본다.
- **검증 출력은 적용 대상에만 찍는다.** 쿠폰이벤트가 아닌 캠페인에 "불변식 ❌"를 표시하면 없는 문제를 있는 것처럼 보고하게 된다.
- **`추가 기간 연장`은 다른 자동화를 건드리지 않는다.** 같은 테이블의 「입금 정산 확인」·「프협 환불 신청」·「쿠폰 자동 발행」은 전부 `recordMatchesConditions`인데, 이미 조건 안/밖에 고정된 레코드는 무관한 필드를 고쳐도 재발사되지 않는다. 「모집폼 작성 완료」는 `recordCreated`라 수정으로는 안 터진다.

## 4. 연장이 답이 아닌 경우

기계적으로 늘리지 말 것. 아래는 **환불·마감이 더 맞을 수 있다** — 사람에게 판단을 넘긴다.

- **신청 0명** — 돈은 받았는데 아무도 안 붙었다. 연장해도 같은 결과일 가능성이 높다.
- **일부만 완료** — 4명 중 2명 콘텐츠 완료·2명 미충원이면 부분 환불이 나을 수 있다.
- **이미 여러 번 연장됨** — `추가 기간 연장`이 크게 쌓였는데 신청이 0이면 연장을 더 쌓는 게 해법이 아니다.
