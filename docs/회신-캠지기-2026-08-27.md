### Q1(3) 화이트리스트 — 초안에서 한 개 바뀌었습니다

```
초안   상태 · 응답 일시 · 거절 상세 사유 · 예외거부 일시
확정   상태 · 응답 일시 · 거절 사유 · 거절 상세 사유
```

`예외거부 일시`를 뺐습니다. Q1(2)에서 **확인 창 거절은 `예외거부`가 아니라고** 합의했으니
포털이 그 필드를 쓸 일이 없습니다. 대신 거절 시 실제로 필요한 `거절 사유`를 넣었습니다.

`멱등키`·`버전`은 금지 유지입니다. 낙관적 잠금 대신 **`응답 일시`가 비어 있을 때만 응답 처리**합니다 —
운영자가 Airtable UI로 직접 고치는 게 정상 경로인데 UI는 버전을 올리지 않아, 버전 잠금은
안전해지지 않고 착각만 만듭니다.

이 4개는 `tools/jimyeong/verify-contract.ts`가 강제합니다. 늘어나면 검증이 FAIL합니다.

## 2. 🔴 확인 창이 시간에서 영업일로 바뀌었습니다

권고해주신 48시간을 사장님이 **2영업일로 바꿨습니다.** 이유는 그쪽 권고의 근거와 같은 방향입니다:
절대시간은 **받은 요일에 따라 실제 여유가 달라집니다.** 금요일 저녁에 받으면 일요일 저녁이 마감입니다.

**포털 구현 (완료 · 배포됨)**

```
마감 = 발송 다음 날부터 세어 2영업일째 되는 날의 23:59:59.999 (KST)

  화 10:00 발송 → 수(1)·목(2)  → 목 자정 직전
  금 18:00 발송 → 월(1)·화(2)  → 화 자정 직전   (48h였다면 일요일 저녁에 잠겼습니다)
  추석 직전 수  → 연휴 전부 건너뛰고 화(1)·수(2)
```

- 상수 `OFFER_RESPONSE_WINDOW_BUSINESS_DAYS = 2`
- 공휴일 `KR_HOLIDAYS` 수동 테이블 + `KR_HOLIDAYS_COVERED_THROUGH = '2026-12-31'`. **커버리지 밖은 주말만 제외**로 폴백
- 계산은 **KST 달력 고정**. 서버가 UTC라 로컬 타임존에 의존하면 자정 근처에서 하루가 밀립니다
- `verify-rules` 107 → **114 passed**

**그쪽에 필요한 것**

1. **`CREATOR_REVIEW_WINDOW_HOURS`(시간 단위)는 더 이상 대응되지 않습니다.** 단위가 다릅니다.
   영업일 계산으로 바꾸시거나, 마감을 포털 계산값 하나만 쓰도록 정리해야 **양쪽이 같은 마감**을 말합니다
2. **공휴일 테이블을 공유해야 합니다.** 각자 관리하면 연휴마다 하루씩 어긋납니다.
   저희 테이블을 단일 소스로 쓰시겠습니까, 그쪽 것을 쓸까요
3. **약관 문구 동기화.** 포털 고지는 *"제안서를 받으시면 2영업일 안에 수락 또는 거절로 회신해주세요
   (주말·공휴일은 세지 않아요)"* 로 고쳤습니다

## 3. 🔴 제안서 메일 두 곳을 고쳐주세요

「지명형 협찬 제안서 크리에이터 발송」(`wflZmG34NnNVuZiHw`) 설정을 열어 확인했습니다.
저희 쪽 MCP 연결은 자동화 **읽기만** 되고 쓰기 권한이 없어, 문구만 드립니다.

### 3-1. 회신 기한이 메일에 없습니다 — 배포 전 필수

현재 본문은 *"이 조건으로 진행 가능하시면 회신해주세요"* 라고만 하고 **기한을 말하지 않습니다.**
그런데 이 자동화가 `크리에이터 발송 일시`를 찍는 순간 **확인 창 시계가 시작됩니다.**
기한을 알려주지 않고 시계를 돌리는 셈이라, 그대로 배포하면 첫 분쟁이 여기서 납니다.

**제안 내용과 맺음말 사이에 아래 블록을 넣어주세요.**

```
---

### ⏳ 회신 기한

**이 메일을 받으신 다음 날부터 2영업일 안에** 수락 또는 거절로 회신해주세요.
주말과 공휴일은 세지 않습니다.

회신이 없으면 **매칭이 확정되지 않습니다.** 임의로 수락 처리되지는 않아요.

---
```

문구가 포털 고지·약관과 **같은 말**이어야 합니다. 한쪽만 고치면 크리에이터가 서로 다른 마감을 두 곳에서 봅니다.

### 3-2. 쿠폰 코드는 지금처럼 넣지 마세요 — 확인 완료

Q2 결정(발행은 발송 전, **노출은 수락 후**)의 전제라 확인했는데, **현재 본문에 코드가 없습니다.**
이미 맞게 되어 있으니 **앞으로도 넣지 말아 주세요.** 메일에 코드가 들어가는 순간
"거절자는 코드를 본 적이 없다"는 구조가 무너지고, 저희가 화면에서 가리는 게 무의미해집니다.

포털도 같은 원칙을 지킵니다: `크리에이터확인중` 상태에서는 **API 응답에도 코드를 담지 않습니다.**

### 3-3. 참고 — 조용한 실패 지점

트리거가 `크리에이터 이메일(조회)` 존재를 요구합니다. 비어 있으면 발송되지 않고 상태가
`입금확인`에 멈춥니다. **캠지기 돈은 이미 들어와 있는 상태**라 알아채기 어렵습니다.
포털에서는 이메일이 공개 필수 항목이라 승인자는 안전하지만, 미공개 크리에이터에게 제안을 만들면 뚫립니다.

## 4. 🔴 심사 SLA가 5영업일로 바뀌었습니다

포털 화면이 *"보통 1영업일"* 이라고 약속하고 있었는데, 심사가 사람 손이라 지킬 수 없는 약속이었습니다.
**5영업일로 고쳤습니다**(배포 완료). 그쪽 문서·약관에 심사 SLA 언급이 있으면 같이 맞춰주세요.

함께 바꾼 것: 심사 결과 자동 통보가 없어 크리에이터가 결과를 모르는 문제가 있었습니다.
**포털 화면에 심사 상태를 명시**하도록 고쳤습니다 — `심사 완료 · 공개 중` / `캠핏 확인 중(보통 5영업일)` /
`심사 반려됨` + 사유 + 재신청 안내. 카톡 통보를 놓쳐도 크리에이터가 화면에서 확인할 수 있습니다.
