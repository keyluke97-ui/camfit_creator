# 협찬 2분기(신청하기 / 제안받기) 진입 IA + 제안받기 CTA 강조

- 작성일: 2026-09-02
- 대상: 크리에이터 포털 (`influencer-portal`) 대시보드
- 브랜치: `feat/sponsorship-two-tracks`

## 1. 배경과 문제

캠핏 협찬은 실제로 두 갈래다.

| 크리에이터가 보는 이름 | 내부 용어 | 동작 |
|---|---|---|
| 신청하기 | 프리미엄 협찬 | 열린 캠페인 목록에서 크리에이터가 지원 |
| 제안받기 | 지명형 협찬 | 프로필을 공개해두면 캠지기가 금액을 얹어 제안 |

**내부 용어 '지명형'은 코드·문서·Airtable에 그대로 둔다.** 이 문서가 바꾸는 것은 크리에이터가 보는 화면의 이름과 배치뿐이다.

지금 대시보드는 이 두 갈래가 대등해 보이지 않는다.

1. `app/dashboard/page.tsx`에서 "신청하기"는 화면 본문(캠페인 목록)이고, "제안받기"는 본문 위에 얹힌 배너 한 줄이다. 크리에이터 입장에서 협찬이 두 종류라는 사실 자체가 화면에 없다.
2. 내 협찬 프로필 배너 문구가 `조건을 걸고 공개하면 캠지기가 제안해요` 하나로 고정이다. 대시보드가 프로필 상태를 **읽지 않기 때문**에, 미등록자·심사대기자·이미 공개 중인 사람에게 전부 같은 말이 나간다. 밋밋함의 원인은 디자인이 아니라 상태 부재다.
3. 상단 배너가 콘텐츠 등록 / 받은 제안 / 내 협찬 프로필 3복층이라, 갈래를 표현할 자리가 없다.

## 2. 목표 / 비목표

**목표**
- 크리에이터가 대시보드 첫 화면에서 협찬 경로가 둘이라는 걸 인지한다.
- "제안받기" 진입(= 프로필 등록)이 눈에 띄고, 지금 자기 상태에서 다음에 할 일이 보인다.
- 상단 배너 복층을 줄인다.

**비목표**
- 지명형 협찬의 기능·정책 변경 (제안 수락/거절 플로우, 금액 규칙, 심사 기준은 그대로)
- 프로필 편집 폼·수신함 **본문** 카피 개편 (헤더까지만)
- 내부 용어 리네이밍, Airtable 필드 변경

## 3. 설계

### 3.1 화면 구조 — 상단 상시 안내 카드

대시보드 `<main>` 최상단에 2카드 블록을 상시 노출한다. 화면 분리(탭)도, 1회성 온보딩도 아니다. 되돌리기 쉽고 기존 배치를 덜 흔든다.

변경 후 상단 순서:

```
[ 협찬 받는 방법 2가지 ]
  ├─ 신청하기   (아웃라인 카드)
  └─ 제안받기   (브랜드 그린 채움 카드)
[ 콘텐츠 등록 배너 ]        ← 유지
[ 캠페인 목록 … ]
```

- **제거**: 받은 제안 배너 (`app/dashboard/page.tsx` 350~376행), 내 협찬 프로필 배너 (378~395행). 둘 다 제안받기 카드가 흡수한다.
- **유지**: `ContentEntryBanner`. 협찬 분기가 아니라 협찬 **이후**의 의무(콘텐츠 업로드)라서 성격이 다르다.
- 시각적 위계: 제안받기만 `bg-brand` 채움. 신규 갈래로 시선을 끌기 위한 의도적 비대칭이며, 신청하기가 열등해 보이지 않도록 양쪽 다 상태 문구를 갖는다.

### 3.2 카드별 내용

**신청하기 카드**

| 조건 | 문구 | `destination` | 탭 동작 |
|---|---|---|---|
| `hasPremiumId` | `열린 캠페인에 지원 · 신청 가능 N개` | `campaigns` | 아래 캠페인 목록으로 스크롤 |
| `!hasPremiumId` | `정산 정보 등록 필요` | `settlement` | `/premium-register`로 이동 |

이동지를 `message`와 함께 판정 결과에 담는다. 제안받기 쪽만 `destination`을 갖고 신청하기 쪽은 화면이 다시 분기하면, "§3.2 표는 한 파일에 있다"는 전제가 절반만 참이 된다.

`N` = `campaigns.filter(c => !c.isClosed).length` (현재 Stats Bar가 쓰는 값과 동일). `fetchCampaigns`는 `premiumId`가 있을 때만 돌므로 미등록자에게 `N`은 항상 0이고, 그 경우 문구 자체가 바뀌므로 0이 노출되지 않는다.

**제안받기 카드** — `reviewStatus`(`'' | 심사대기 | 승인 | 반려`)와 `isPublic`, `offerCount`, `pendingCount`로 결정한다.

`pendingCount` = 받은 제안 중 상태가 `크리에이터확인중`인 건수. `offerCount`와 반드시 구분한다 — `getCreatorOffers`(`lib/airtable.ts`)는 `크리에이터확인중`과 `확정`을 **둘 다** 읽는다(수락한 제안의 쿠폰 코드를 보여줘야 해서 의도적). 그래서 `offerCount`에 회신 촉구를 걸면, 3건을 전부 수락해 할 일이 없는 사람에게도 "기한 안에 회신해주세요"가 나간다.

| # | 조건 | state | 뱃지 | 문구 | 이동 |
|---|---|---|---|---|---|
| 1 | `'반려'` && `pendingCount === 0` | `REJECTED` | `수정 필요` | 반려 사유를 확인하고 다시 공개해주세요 | `profile` |
| 2 | **제안 있음** (`offerCount > 0 \|\| pendingCount > 0`) | `hidden` ? `HIDDEN_WITH_OFFERS` : `HAS_OFFERS` | 아래 규칙 | 아래 규칙 | **`offers`** |
| 3 | `'심사대기'` | `UNDER_REVIEW` | `심사 중` | 공개 신청 확인 중이에요 | `profile` |
| 4 | `'승인'` && `!isPublic` | `HIDDEN` | `비공개` | 공개로 바꾸면 제안을 받을 수 있어요 | `profile` |
| 5 | `'승인'` && `isPublic` | `WAITING` | 없음 | 캠지기가 볼 수 있어요 · 제안을 기다리는 중 | `profile` |
| 6 | 그 외 (`''` · 알 수 없는 값) | `UNREGISTERED` | `NEW` | 내가 정한 금액부터 제안이 시작됩니다 | `profile` |

**평가 순서는 위 번호 순이며, 처음 참이 되는 행 하나만 적용한다.**

2번 행의 뱃지·문구 규칙. `hidden` = `reviewStatus === '승인' && !isPublic`:

| 갈래 | 값 |
|---|---|
| 뱃지 — `hidden` | `비공개` |
| 뱃지 — `!hidden` && `newOfferCount > 0` | `새 제안 {newOfferCount}` |
| 뱃지 — 그 외 | 없음 |
| 문구 — `pendingCount > 0` | `받은 제안 {pendingCount}건 · 기한 안에 회신해주세요` |
| 문구 — `pendingCount === 0` | `확정된 제안 {offerCount}건 확인하기` |

- **2번이 3·4·5·6번보다 위에 있는 것이 이 표의 핵심이다.** 받은 제안 배너를 없앤 뒤로 `/dashboard/offers`로 가는 링크는 이 카드 하나뿐이고, 회신 기한은 2영업일이라 링크가 사라지면 그대로 만료된다. 그래서 제안 보유가 심사 상태·공개 여부보다 앞선다.
- **1번(반려)이 제안보다 위인 것은 `pendingCount === 0`일 때뿐이다.** 게이트를 `offerCount`로 잡으면 안 된다 — `getCreatorOffers`가 `크리에이터확인중`과 `확정`을 함께 읽고 확정 제안은 목록에서 사라지지 않으므로, 확정 제안 하나만 있어도 "수정 필요"가 **영구히 가려진다**. 반대로 회신 대기 건이 있는 동안에는 수신함이 앞선다 — 기한이 2영업일이라 여기서 링크를 가리면 그대로 만료되기 때문이다. 대기 건을 회신하면 카드가 반려로 돌아오므로 **은폐가 아니라 일시 양보**이고, 그 사이에도 반려 사유로 가는 길은 §3.5의 수신함 헤더 링크가 잇는다.
- **`심사대기`는 제안보다 아래다.** `심사 중`은 비행동성 안내이고 프로필 화면에도 있으므로 잠시 가려도 손실이 작다. 반대로 여기서 제안을 가리면 실제로 만료된다 — 그리고 이 조합은 **크리에이터가 직접 만든다**: 운영자가 미등록자에게 제안을 보내 카드가 수신함으로 유도 → 크리에이터가 프로필 등록 후 공개 신청 → `lib/airtable.ts`의 `'' | '반려' → '심사대기'` 전이(크리에이터 주도다. 심사 필드를 payload로 못 바꿀 뿐, 이 전이는 공개 신청으로 일어난다) → 링크 소실.
- **`비공개` 뱃지는 `승인`일 때만 붙인다.** 폴백은 `isPublic`을 아예 모르고(기본값 `false`), `심사대기`의 `isPublic`도 믿을 신호가 아니다 — `PublishRequestCard`의 "공개 중지하기" 버튼은 심사 상태와 무관하게 뜨고, 눌러도 심사대기는 유지된다(`lib/airtable.ts`의 심사 전이 분기가 `isPublic && ('' | '반려')`와 `승인` 둘뿐이라 `심사대기`를 다루지 않는다). 그래서 `심사대기`의 `false`는 "심사 중인데 비공개"일 수도, 그냥 기본값일 수도 있다. **확실한 건 `승인 && !isPublic` 하나뿐이다.** 그 결과 `심사대기` × 실제 비공개인 사람에겐 뱃지가 누락되지만, 이동지가 수신함이라 손해가 작다 — 없는 사실을 말하는 것보다 낫다.
- `NEW` 뱃지는 **6번(미등록)에서만** 뜬다. 한 번 등록하면 사라지므로 뱃지가 소진되지 않는다.
- `새 제안 N`의 N은 기존 `newOfferCount` — `lib/offerSeen.ts`의 `unseenIds(...)` 결과 길이. 계산 방식을 바꾸지 않는다.
- 1번(반려)만 위험 색을 쓰고 나머지는 브랜드 그린을 유지한다. `app/globals.css`에 `text-danger` 토큰은 없다 — 기존 코드처럼 `text-red-*`/`bg-red-*`를 쓴다(`components/OfferRejectForm.tsx` 참조).
- **프로필 조회가 끝나기 전에는 6번을 쓰지 않는다.** 기본값(`reviewStatus: ''` + `isPublic: false`)이 하필 미등록과 같아서, 그냥 두면 매 진입마다 이미 승인·공개된 사람에게도 `NEW` 뱃지가 깜빡인다 — `NEW`를 미등록에서만 띄워 소진을 막겠다는 설계가 무너진다. 패칭이 끝날 때까지는 `OFFER_TRACK_LOADING`(`협찬 조건을 불러오는 중이에요`, 뱃지 없음)을 쓴다. 단 제안 건수는 별도 패칭이라 이미 알 수 있으므로, **제안이 있으면 로딩 중에도 2번을 그대로 쓴다.**
- 프로필 조회 실패 시 제안이 있으면 2번, 없으면 6번으로 폴백한다. 최악의 경우 이미 등록한 사람에게 등록 유도가 한 번 더 보일 뿐, 화면이 깨지거나 제안이 숨겨지지 않는다.

### 3.3 상태 소스 — 기존 `/api/creator/profile` GET 재사용

대시보드에서 캠페인·제안 fetch와 **병렬로** `GET /api/creator/profile`을 호출하고 `reviewStatus`·`isPublic`만 사용한다.

- `getCreatorProfile`(`lib/airtable.ts`)은 `creatorTable().find(creatorId)` 단건 조회 + 정산 요약이라 비용이 작다. 신규 라우트가 필요 없고 프로필 스키마의 진실 소스가 한 곳으로 유지된다.
- 요약 엔드포인트 신설안은 라우트 + JWT 가드 한 벌이 늘고 스키마 변경 시 고칠 자리가 둘로 갈라져서 버렸다.
- `/api/auth/me`에 얹는 안은 로그인 시점에 굳는 사용자 정보에 **변하는 상태**를 섞게 되어, 프로필을 고치고 돌아와도 카드가 안 바뀌는 버그를 부른다. 버렸다.
- 실패는 조용히 처리한다(`console.error` 후 폴백). 기존 `fetchPendingCheckinCount`·offers 패칭과 같은 패턴이다. 제안받기는 부가 경로라, 여기서 에러 배너를 띄우면 프리미엄 협찬을 쓰러 온 사람에게 상관없는 경고가 뜬다.

### 3.4 컴포넌트 경계

`app/dashboard/page.tsx`는 이미 726줄이다. 카드 블록을 인라인 JSX로 더 넣지 않는다.

**신규 `lib/sponsorshipTrackRules.ts`** — 순수 판정 로직

§3.2 표의 상태 → 뱃지·문구·이동 매핑을 순수 함수로 둔다. React·Airtable SDK에 의존하지 않는다. `lib/creatorProfileRules.ts`·`lib/offerRules.ts`와 같은 자리·같은 이유다 — `tools/jimyeong/verify-rules.ts`가 `npx tsx`로 직접 돌려 검증할 수 있어야 한다(이 레포엔 테스트 러너가 없다). **크리에이터에게 나가는 문구는 전부 이 파일에 있고, 카피 수정은 여기서만 한다.**

**신규 `components/SponsorshipTracks.tsx`** (`export default`, `'use client'`) — 표현만

```ts
interface SponsorshipTracksProps {
    openCampaignCount: number;
    hasPremiumId: boolean;
    offerCount: number;
    pendingCount: number;
    newOfferCount: number;
    reviewStatus: ReviewStatus;
    isPublic: boolean;
    onApplyClick: (destination: ApplyTrackDestination) => void;
    onOfferClick: (destination: OfferTrackDestination) => void;
}
```

- 문구·뱃지는 `sponsorshipTrackRules`가 정한다. 이 파일엔 표현만 둔다. `page.tsx`는 값만 넘기고 문구를 모른다.
- **어디로 갈지는 판정 로직이, 어떻게 갈지는 `page.tsx`가 정한다.** 카드는 `destination`을 그대로 콜백에 넘기고 라우터를 직접 잡지 않는다 — 스크롤 동작(신청하기)과 페이지 이동(제안받기)이 한 컴포넌트에 섞이지 않게.
- 스크롤 타깃: 캠페인 목록 섹션에 `id`를 부여하고 `scrollIntoView({ behavior: 'smooth' })`.

**`page.tsx` 변경**
- 위 두 배너 JSX 삭제, `<SponsorshipTracks />` 삽입
- `reviewStatus`·`isPublic` state 추가 + 프로필 fetch useEffect 1개 추가
- 기존 offers useEffect에서 `pendingCount`(상태 `크리에이터확인중`) 집계 추가
- `offerCount`·`newOfferCount` state는 그대로 두고 props로 내려보낸다

### 3.5 카피 (헤더까지)

| 위치 | 현재 | 변경 |
|---|---|---|
| `app/dashboard/portfolio/page.tsx` `<h1>` | 내 협찬 프로필 | 제안받기 · 내 프로필 |
| `app/dashboard/offers/page.tsx` `<h1>` | 받은 제안 | 제안받기 · 받은 제안 |

두 화면의 **본문** 카피는 건드리지 않는다.

**추가 — `/dashboard/offers` 헤더에 프로필 링크 상시 노출.** 카피 변경이 아니라 도달성 복구다(§6 참조). 기존 `내 협찬 프로필 보기` 버튼은 `offers.length === 0` 빈 상태 안에만 있어서, 제안이 생기는 순간 사라진다.

## 6. 리스크

- **배너 2개 제거**로 기존 사용자의 근육 기억이 깨진다.
- ⚠️ **제안받기 카드는 한 번에 한 곳으로만 간다.** 두 배너를 하나로 합치면서 "둘 다 접근 가능"이 "둘 중 하나만 접근 가능"으로 바뀐다. 제안이 있으면 카드가 수신함으로 가므로, **확정 제안을 보유한 크리에이터는 프로필로 갈 길을 잃는다** — 확정 제안은 `getCreatorOffers` 목록에서 사라지지 않아 영구적이다. 협찬을 성사시킨 사람일수록 자기 조건을 못 고치게 되는 회귀라, `/dashboard/offers` 헤더에 프로필 링크를 상시 노출해 복구한다(§3.5).
- ⚠️ **`pendingCount`는 상태(`크리에이터확인중`) 기준이라 기한이 지난 미응답 건이 영구히 남을 수 있다.** 그러면 반려 크리에이터의 "수정 필요" 안내가 카드에서 계속 가려진다. 지금은 수신함 헤더의 `내 프로필` 링크가 그 경로를 잇지만, 별도 작업(기한 지난 미응답 제안 상태 정리)이 끝나면 이 조합을 다시 본다.
- 대시보드 진입 시 API 호출이 1건 늘어난다(병렬). 단건 조회라 체감 지연은 없을 것으로 보나, 느리면 §3.3의 요약 엔드포인트안으로 후퇴한다.
