# 협찬 2분기(신청하기 / 제안받기) 진입 IA + 제안받기 CTA 강조

- 작성일: 2026-09-02
- 대상: 크리에이터 포털 (`influencer-portal`) 대시보드
- 브랜치: `feat/sponsorship-two-tracks`

## 1. 배경과 문제

캠핏 협찬은 실제로 두 갈래다.

| 크리에이터가 보는 이름 | 내부 용어 | 동작 |
|---|---|---|
| 신청하기 | 프리미엄 협찬 | 열린 캠페인 목록에서 크리에이터가 지원 |
| 제안받기 | 지명형 협찬 | 프로필을 공개해두면 캠지기가 금액을 얹어 제안 |

**내부 용어 '지명형'은 코드·문서·Airtable에 그대로 둔다.** 이 문서가 바꾸는 것은 크리에이터가 보는 화면의 이름과 배치뿐이다.

지금 대시보드는 이 두 갈래가 대등해 보이지 않는다.

1. `app/dashboard/page.tsx`에서 "신청하기"는 화면 본문(캠페인 목록)이고, "제안받기"는 본문 위에 얹힌 배너 한 줄이다. 크리에이터 입장에서 협찬이 두 종류라는 사실 자체가 화면에 없다.
2. 내 협찬 프로필 배너 문구가 `조건을 걸고 공개하면 캠지기가 제안해요` 하나로 고정이다. 대시보드가 프로필 상태를 **읽지 않기 때문**에, 미등록자·심사대기자·이미 공개 중인 사람에게 전부 같은 말이 나간다. 밋밋함의 원인은 디자인이 아니라 상태 부재다.
3. 상단 배너가 콘텐츠 등록 / 받은 제안 / 내 협찬 프로필 3복층이라, 갈래를 표현할 자리가 없다.

## 2. 목표 / 비목표

**목표**
- 크리에이터가 대시보드 첫 화면에서 협찬 경로가 둘이라는 걸 인지한다.
- "제안받기" 진입(= 프로필 등록)이 눈에 띄고, 지금 자기 상태에서 다음에 할 일이 보인다.
- 상단 배너 복층을 줄인다.

**비목표**
- 지명형 협찬의 기능·정책 변경 (제안 수락/거절 플로우, 금액 규칙, 심사 기준은 그대로)
- 프로필 편집 폼·수신함 **본문** 카피 개편 (헤더까지만)
- 내부 용어 리네이밍, Airtable 필드 변경

## 3. 설계

### 3.1 화면 구조 — 상단 상시 안내 카드

대시보드 `<main>` 최상단에 2카드 블록을 상시 노출한다. 화면 분리(탭)도, 1회성 온보딩도 아니다. 되돌리기 쉽고 기존 배치를 덜 흔든다.

변경 후 상단 순서:

```
[ 협찬 받는 방법 2가지 ]
  ├─ 신청하기   (아웃라인 카드)
  └─ 제안받기   (브랜드 그린 채움 카드)
[ 콘텐츠 등록 배너 ]        ← 유지
[ 캠페인 목록 … ]
```

- **제거**: 받은 제안 배너 (`app/dashboard/page.tsx` 350~376행), 내 협찬 프로필 배너 (378~395행). 둘 다 제안받기 카드가 흡수한다.
- **유지**: `ContentEntryBanner`. 협찬 분기가 아니라 협찬 **이후**의 의무(콘텐츠 업로드)라서 성격이 다르다.
- 시각적 위계: 제안받기만 `bg-brand` 채움. 신규 갈래로 시선을 끌기 위한 의도적 비대칭이며, 신청하기가 열등해 보이지 않도록 양쪽 다 상태 문구를 갖는다.

### 3.2 카드별 내용

**신청하기 카드**

| 조건 | 문구 | 탭 동작 |
|---|---|---|
| `hasPremiumId` | `열린 캠페인에 지원 · 신청 가능 N개` | 아래 캠페인 목록으로 스크롤 |
| `!hasPremiumId` | `정산 정보 등록 필요` | `/premium-register`로 이동 |

`N` = `campaigns.filter(c => !c.isClosed).length` (현재 Stats Bar가 쓰는 값과 동일). `fetchCampaigns`는 `premiumId`가 있을 때만 돌므로 미등록자에게 `N`은 항상 0이고, 그 경우 문구 자체가 바뀌므로 0이 노출되지 않는다.

**제안받기 카드** — `reviewStatus`(`'' | 심사대기 | 승인 | 반려`)와 `isPublic`, `offerCount`로 결정한다.

| # | 조건 | 뱃지 | 문구 | 이동 |
|---|---|---|---|---|
| 1 | `reviewStatus === ''` | `NEW` | 내가 정한 금액부터 제안이 시작됩니다 | `/dashboard/portfolio` |
| 2 | `'심사대기'` | `심사 중` | 공개 신청 확인 중이에요 | `/dashboard/portfolio` |
| 3 | `'반려'` | `수정 필요` | 반려 사유를 확인하고 다시 공개해주세요 | `/dashboard/portfolio` |
| 4 | `'승인'` && `!isPublic` | `비공개` | 공개로 바꾸면 제안을 받을 수 있어요 | `/dashboard/portfolio` |
| 5 | `'승인'` && `isPublic` && `offerCount > 0` | `새 제안 N` (N>0일 때만) | 받은 제안 N건 · 기한 안에 회신해주세요 | `/dashboard/offers` |
| 6 | `'승인'` && `isPublic` && `offerCount === 0` | 없음 | 캠지기가 볼 수 있어요 · 제안을 기다리는 중 | `/dashboard/portfolio` |

**평가 순서는 위 표의 번호 순이며, 처음 참이 되는 행 하나만 적용한다.** 4·5·6은 모두 `'승인'` 하위라 `isPublic` → `offerCount` 순으로 갈라진다.

- `NEW` 뱃지는 **1번(미등록)에서만** 뜬다. 한 번 등록하면 사라지므로 뱃지가 소진되지 않는다.
- `새 제안 N`의 N은 기존 `newOfferCount` — `lib/offerSeen.ts`의 `unseenIds(...)` 결과 길이. 계산 방식을 바꾸지 않는다.
- 3번(반려)만 위험 색(`text-danger` 계열)을 쓰고 나머지는 브랜드 그린을 유지한다.
- 프로필 조회 실패 시 1번(미등록)으로 폴백한다. 최악의 경우 이미 등록한 사람에게 등록 유도가 한 번 더 보일 뿐, 화면이 깨지거나 제안이 숨겨지지 않는다.

### 3.3 상태 소스 — 기존 `/api/creator/profile` GET 재사용

대시보드에서 캠페인·제안 fetch와 **병렬로** `GET /api/creator/profile`을 호출하고 `reviewStatus`·`isPublic`만 사용한다.

- `getCreatorProfile`(`lib/airtable.ts`)은 `creatorTable().find(creatorId)` 단건 조회 + 정산 요약이라 비용이 작다. 신규 라우트가 필요 없고 프로필 스키마의 진실 소스가 한 곳으로 유지된다.
- 요약 엔드포인트 신설안은 라우트 + JWT 가드 한 벌이 늘고 스키마 변경 시 고칠 자리가 둘로 갈라져서 버렸다.
- `/api/auth/me`에 얹는 안은 로그인 시점에 굳는 사용자 정보에 **변하는 상태**를 섞게 되어, 프로필을 고치고 돌아와도 카드가 안 바뀌는 버그를 부른다. 버렸다.
- 실패는 조용히 처리한다(`console.error` 후 폴백). 기존 `fetchPendingCheckinCount`·offers 패칭과 같은 패턴이다. 제안받기는 부가 경로라, 여기서 에러 배너를 띄우면 프리미엄 협찬을 쓰러 온 사람에게 상관없는 경고가 뜬다.

### 3.4 컴포넌트 경계

`app/dashboard/page.tsx`는 이미 726줄이다. 카드 블록을 인라인 JSX로 더 넣지 않는다.

**신규 `components/SponsorshipTracks.tsx`** (`export default`, `'use client'`)

```ts
interface SponsorshipTracksProps {
    openCampaignCount: number;
    hasPremiumId: boolean;
    offerCount: number;
    newOfferCount: number;
    reviewStatus: ReviewStatus;
    isPublic: boolean;
    onApplyClick: () => void;
    onOfferClick: () => void;
}
```

- **§3.2 표의 상태 → 뱃지·문구 매핑을 이 파일 안 순수 함수로 둔다.** 카피를 고칠 때 열 파일이 하나가 되도록. `page.tsx`는 값만 넘기고 문구를 모른다.
- 이동 경로는 `page.tsx`가 정한다(`onApplyClick`/`onOfferClick`). 카드가 라우터를 직접 잡으면 스크롤 동작(신청하기)과 페이지 이동(제안받기)이 한 컴포넌트에 섞인다.
- 스크롤 타깃: 캠페인 목록 섹션에 `id`를 부여하고 `scrollIntoView({ behavior: 'smooth' })`.

**`page.tsx` 변경**
- 위 두 배너 JSX 삭제, `<SponsorshipTracks />` 삽입
- `reviewStatus`·`isPublic` state 추가 + 프로필 fetch useEffect 1개 추가
- `offerCount`·`newOfferCount` state는 그대로 두고 props로 내려보낸다

### 3.5 카피 (헤더까지)

| 위치 | 현재 | 변경 |
|---|---|---|
| `app/dashboard/portfolio/page.tsx` `<h1>` | 내 협찬 프로필 | 제안받기 · 내 프로필 |
| `app/dashboard/offers/page.tsx` `<h1>` | 받은 제안 | 제안받기 · 받은 제안 |

두 화면의 **본문** 카피는 건드리지 않는다.

## 4. 에러 처리

| 실패 | 결과 |
|---|---|
| `/api/creator/profile` 실패 | `console.error` + 제안받기 카드가 1번(미등록) 상태로 표시 |
| `/api/offers` 실패 | 기존과 동일 — `offerCount` 0 유지 → 카드가 4/6번으로 표시 |
| `/api/campaigns` 실패 | 기존과 동일 — 신청하기 카드에 `신청 가능 0개` |

세 실패 모두 대시보드 본문은 정상 렌더된다.

## 5. 검증

- `npm run lint` 통과
- 수동 확인 6종 — 정산정보 미등록 / 프로필 미등록 / 심사대기 / 반려 / 승인·공개·제안 0건 / 승인·공개·제안 N건. Airtable에서 테스트 계정의 `심사상태`·`프로필 공개`를 바꿔가며 확인한다.
- `NEW` 뱃지가 프로필 등록 후 사라지는지 확인 (1번 → 2번 전이)
- 모바일 폭(`max-w-md`)에서 2카드 + 콘텐츠 배너 이후 캠페인 목록 첫 카드가 한 화면 스크롤 안에 들어오는지 확인

## 6. 리스크

- **배너 2개 제거**로 기존 사용자의 근육 기억이 깨진다. 두 진입점 모두 제안받기 카드 안에 남으므로 기능 손실은 없다.
- 대시보드 진입 시 API 호출이 1건 늘어난다(병렬). 단건 조회라 체감 지연은 없을 것으로 보나, 느리면 §3.3의 요약 엔드포인트안으로 후퇴한다.
