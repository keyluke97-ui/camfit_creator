### Q1(2) 거절은 `예외거부`가 아니다 — 둘은 다른 것이다

스키마에 `예외거부`·`예외거부 일시`·`예외 거부 사용 횟수`가 있어 그쪽으로 보이지만, **확인 창 거절을 여기 넣으면 확인 창을 만든 이유가 사라진다.**

| | 뜻 | 횟수 제한 |
|---|---|---|
| `예외거부` | **확정된 건**을 제한적으로 되무르는 안전판 | 있음 |
| 확인 창 거절 | **확정 전** 정상 응답 | 없어야 함 |

07-31에 확인 창을 도입한 근거가 *"예외 거부권은 횟수 제한 카드라 '캠핑장이 마음에 안 들어서' 쓰기엔 비싸다"* 였다. 확인 창 거절이 그 횟수를 소모하면 원래 문제가 그대로 남는다.

→ **구 `거절` 옵션을 재사용한다.** Airtable이 select 옵션 삭제를 지원하지 않아 어차피 남아 있고 뜻도 정확히 맞다. 새로 만들면 뜻이 겹치는 옵션이 둘 생긴다.

### Q1(3) ✅ 쓰기 화이트리스트 — 사장님 승인 (2026-08-26)

v2 §9는 *"포털은 `지명 제안`에 쓰지 않는다"* 였다. 그런데 1b는 크리에이터가 실시간 응답하는 화면이라, 플래그만 세우고 자동화가 옮기면 **수락을 눌렀는데 화면이 안 바뀐다.**

```
허용   상태 · 응답 일시 · 거절 사유 · 거절 상세 사유
금지   그 외 전부 — 특히 금액 4종 · 제안서 전문 · 조건 스냅샷
```

금액과 스냅샷이 핵심이다. 분쟁 시 증거인데 쓰기 권한이 두 곳으로 갈리면 "누가 바꿨나"를 못 가린다. **이 화이트리스트를 `verify-contract`로 강제한다.**

> ✅ **두 구멍 해소 (2026-08-26 승인본)**
> - `거절 사유`(singleSelect 일정/금액/기타)를 **허용 목록에 넣었다.** 대신 `예외거부 일시`를 뺐다 —
>   확인 창 거절은 `예외거부`가 아니므로(Q1(2)) 포털이 그 필드를 쓸 일이 애초에 없다
> - `멱등키`·`버전`은 금지 유지 → 낙관적 잠금 대신 **`응답 일시`가 비어 있을 때만 응답 처리.**
>   캠지기측 「제안서 발송」 자동화가 `크리에이터 발송 일시`로 중복을 막는 것과 같은 패턴이고,
>   허용 필드만 쓴다. 이 레포의 `applyCampaign` 2단계 검증(사전 체크 + 사후 검증 + 롤백)과도 맞는다
>   (버전 잠금이 성립하지 않는 이유 — 운영자가 Airtable UI로 직접 고치는 게 정상 경로인데 UI는 버전을 안 올린다)

### Q3 ✅ 완료 — 포털 문구를 고쳤다

```
before  응답이 없으면 수락한 것으로 자동 확정됩니다
after   제안서를 받으시면 24~48시간 안에 수락 또는 거절로 회신해주세요
        회신이 늦어지면 캠핏이 연락드려요. 임의로 수락 처리되지는 않아요
```

자동 확정은 **설계에는 있고 구현에는 없다**(양쪽이 독립으로 자동화 전수 확인).

> ⚠️ **2단계에서 자동 확정을 켤 때는 이 고지 동의를 다시 받아야 한다.**
> 지금 회신 요구로 고쳐놓고 나중에 조용히 켜면 지금보다 더 나쁘다 — 그때는 크리에이터에게
> *"그런 줄 몰랐다"* 고 할 근거가 오히려 생긴다.

### Q4 ✅ 오픈 시점엔 숫자를 쓰지 않는다

*"3회"* 라고 쓰면 3회째에 집행해야 하는데 집행 로직이 없다. **Q3과 같은 종류의 거짓말이다.**
현재 문구(*"거절이 반복되면 서비스 이용이 제한될 수 있어요"*)로 두고, 사례가 쌓인 뒤 기준을 정해 고지를 갱신한다. `예외 거부 사용 횟수`는 **세기만** 한다 — 세는 것과 집행하는 것은 다르다.

### Q2 ✅ 발행은 발송 전, **코드 노출은 수락 후** — 사장님 확정 (2026-08-26)

캠지기측 의심은 *"거절해도 쿠폰이 이미 손에 있고 회수 절차가 없다"* 였다.
사장님 답은 **발행 시점과 노출 시점을 분리**해 그 리스크 자체를 없앤다.

```
캠지기 신청 → 입금확인 → 쿠폰 발행(수기) → 크리에이터 제안 발송   ← 여기까지 코드는 안 보인다
                                              ↓ 수락
                                        이미 발행된 코드를 그때 보여준다
```

**왜 이 순서인가**

- 발행을 확정 뒤로 미루면 **운영자가 한 번 더 일한다.** 발행이 수기라 입금확인 흐름에서 한 번에 끝내는 게 맞다
- 그런데 **코드를 안 보여주면 거절자는 코드를 가진 적이 없다.** 회수 절차가 필요 없어진다 —
  절차를 만들어 지키는 대신 **지킬 게 없게** 만든 것이다
- 거절·무응답 건의 코드는 그대로 **다음 제안에 재배포**한다. 아무도 본 적 없는 코드이므로 안전하다

지명형은 `크리에이터 쿠폰 코드`가 **`지명 제안` 레코드 단위 필드**라 1:1이고, 그래서 재배포가 성립한다
(프리미엄은 캠페인 단위 lookup — `크리에이터 쿠폰 코드 (from 캠페인)`. 구조가 다르다).

> 🔴 **이 결정은 포털만으로 지켜지지 않는다 — 캠지기측 확인 필요.**
> 「제안서 발송」 자동화가 보내는 **메일 본문에 쿠폰 코드가 들어가면 노출 시점 분리가 무너진다.**
> 메일에는 코드를 넣지 않고 포털 링크만 보내야 한다. 회신에 포함시켰다.

## 1-2. 🔴 확인 창 기산점은 `만료 예정 일시`가 아니다 (2026-08-25 정정)

`만료 예정 일시`는 **캠지기의 선입금 기한**이다(제안 생성 +48h). 확인 창 마감이 아니다.

**실측 근거 3가지**

```
① 크리에이터 발송 일시(fldKgBIVR8dWWnxZj) description
   "…중복 발송 방지·확인 창(24~48h) 기산점. 확정필드 v2 §4"

② 선입금 만료 도래 포뮬러
   IF(AND({상태} = "선입금대기", IS_AFTER(NOW(), {만료 예정 일시})), 1, 0)
                  ^^^^^^^^^^^^ 선입금대기일 때만 본다

③ 「제안서 발송」 자동화의 updateRecord가 쓰는 필드 (get_automation 실측)
   크리에이터 발송 일시 = 실행 시각
   상태 = 크리에이터확인중
   → 만료 예정 일시는 건드리지 않는다
```

**그래서 어떻게 되나**

```
제안 생성 (만료 예정 일시 = +48h)
  → 캠지기 입금
  → 운영자 입금 대사        ← 수기다. 48시간을 넘기는 게 정상이다
  → 캠핑장 링크 입력
  → 제안서 발송 체크
  → 크리에이터확인중        ← 이 시점에 만료 예정 일시는 이미 지나 있다
```

`만료 예정 일시`를 응답 기한으로 쓰면 **거의 모든 제안이 열리자마자 마감된 것으로 잠긴다.**
피하려던 상황(*"캠지기 돈은 들어와 있는데 제안이 아무 데도 못 간다"*)이 기본 경로가 된다.

→ **기산점 = `크리에이터 발송 일시` + `OFFER_RESPONSE_WINDOW_HOURS`.**
   `만료 예정 일시`는 1b에서 쓰지 않는다 — 선입금 페이지(캠지기측)가 쓰는 필드다.

✅ **창 길이 = 2영업일 확정 (2026-08-26 사장님).** 캠지기 권고는 48시간이었으나 **절대시간을 폐기했다.**

> 절대시간은 **받은 요일에 따라 실제 여유가 달라진다.** 금요일 저녁에 받으면 일요일 저녁이 마감이라
> 손쓸 시간이 없고, 화요일 아침에 받으면 이틀이 온전히 남는다. 영업일로 세면 누가 언제 받든 같다.

**마감 = 발송 다음 날부터 세어 2영업일째 되는 날의 23:59:59.999 (KST).**
"N영업일 내"의 통상 해석대로 **그날 끝**까지 준다 — 시각을 맞춰 자르면(금 18:00 → 화 18:00)
마감이 근무시간 밖에 걸려 사람이 못 본 채로 지난다.

- 상수 `OFFER_RESPONSE_WINDOW_BUSINESS_DAYS = 2` · 공휴일 테이블 `KR_HOLIDAYS`(수동 관리, 커버리지 밖은 주말만 제외로 폴백)
- 계산은 **KST 달력 고정.** 서버가 UTC(Vercel)라 로컬 타임존에 의존하면 자정 근처에서 하루가 밀린다
- 🔴 **캠지기 상수도 함께 바뀌어야 한다** — `CREATOR_REVIEW_WINDOW_HOURS`(시간 단위)는 더 이상 대응되지 않는다. 회신에 포함
- **상수 한 곳에만** 두고 화면에 숫자를 박지 않는다(바뀔 때 한 곳만 고치게)

> `크리에이터 발송 일시`가 비었는데 상태가 `크리에이터확인중`이면 **응답 가능 + 마감 없음.**
> 자동화를 안 거치고 운영자가 상태만 수기로 옮긴 경우다(자동화가 undeployed라 지금은 이게
> 유일한 경로이기도 하다).

### Q1. `크리에이터확인중` 이후 전이가 정의돼 있지 않다

계약서 v2 §4.2는 `입금확인` → `크리에이터확인중`까지만 정의한다. 그 다음이 없다.

- **수락하면 어느 상태로 가나?** `확정`인가, 중간 상태가 있나?
- **거절하면?** `거절`인가 `예외거부`인가
  (스키마에 `예외거부` 상태 + `예외거부 일시` 필드 + `거절 상세 사유`가 이미 있다 — 의도가 있어 보인다)
- 상태 이동을 **포털이 직접 쓰나**, 아니면 포털은 플래그만 세우고 자동화가 옮기나

### Q2. 쿠폰은 언제 누구에게 가나

사장님 설명: *"수락 전에 해당 캠핑장 쿠폰을 크리에이터에게 주고, 그걸로 예약하는 구조(프협과 유사)"*

스키마에 `크리에이터 쿠폰 코드` · `🎟️ 발행 상태` · `🎟️ 발행 일시`가 있고, 계약서엔 발행 시점이 안 나온다.

- 쿠폰 발행이 **수락 전**인가 **수락 후**인가

> 아이콘 복제 계정(같은 사람의 두 번째 계정)과 채널명 공백 변형 이슈가 이미 있다.

>
> → **수식은 상태만 거르고, 소유권은 `fields`가 돌려주는 레코드 ID 배열(`includes`)로 판정한다.**
